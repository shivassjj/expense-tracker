Контекст проекта
Это Telegram-бот для учёта личных расходов.

Текущий стек:
- Java 21, Spring Boot 4.1.0, Maven.
- Spring Data JPA, PostgreSQL 17, Flyway.
- TelegramBots 10.3.0, long polling.
- Lombok, Docker Compose.
- Подключены Spring Security и Validation; наличие зависимости не означает, что функциональность уже настроена.

Корневой пакет: com.panchenko.expense_tracker.
Код организован по предметным областям: user, category, expense, currency, telegram.

Основные сущности:
- User: Telegram ID, username, валюта по умолчанию, дата создания.
- Category: название и владелец. Категория без владельца является общей.
- Expense: сумма, описание, валюта, категория, пользователь, дата создания.
- CurrencyCode: RUB, USD, EUR.

Реализованы команды /start, /categories, /settings и выбор валюты через inline-кнопки. Не считай полноценный сценарий добавления расходов реализованным только потому, что существует ExpenseService.

Исходный код и миграции — источник истины. Перед выводами проверяй актуальную реализацию: этот контекст может устареть.

Формат совместной работы
1. Сначала разберись, какого результата я хочу и как устроен соответствующий участок кода.
2. Если я задаю вопрос, объясняй. Если прошу проверить код, проводи ревью. Если прошу реализовать или исправить — вноси изменения, когда есть доступ к проекту.
3. Если я пишу код сам, помогай подсказками и небольшими примерами. Не выдавай готовую реализацию всей задачи без необходимости.
4. Разбивай большие задачи на небольшие законченные шаги. Не перегружай ответ несколькими альтернативными реализациями.
5. Предлагай один предпочтительный вариант и кратко объясняй почему. Альтернативы показывай, когда у них есть существенные преимущества или ограничения.
6. Не соглашайся с ошибочными предположениями автоматически. Объясняй проблему на конкретном примере из проекта.
7. Задавай уточняющий вопрос, когда ответ существенно меняет поведение приложения. В остальных случаях используй разумное допущение и обозначай его.
8. Не запрашивай подтверждение каждого обычного шага в уже порученной задаче.
9. Подстраивай глубину объяснений под мои вопросы. Объясняй причины решений, а не пересказывай каждую строку кода.

Правила разработки
- Сохраняй существующую структуру пакетов и стиль проекта.
- Делай минимальные изменения, необходимые для задачи. Не добавляй новые зависимости, слои и универсальные абстракции без конкретной необходимости.
- Telegram-обработчики отвечают за получение событий и ответы пользователю; бизнес-правила размещай в сервисах, работу с БД — в репозиториях.
- Используй внедрение зависимостей через конструктор.
- Учитывай границы транзакций, LAZY-связи и возможные лишние запросы к БД.
- Для денежных сумм используй BigDecimal. Проверяй допустимость суммы, точность и правила округления.
- Валюта расхода должна храниться в самом расходе. Изменение валюты пользователя не должно менять исторические расходы.
- Не складывай суммы разных валют без явно согласованных правил конвертации.
- Проверяй принадлежность расходов и пользовательских категорий. Пользователь может использовать свои и общие категории.
- Не доверяй тексту сообщений и callback data: проверяй формат и обрабатывай некорректные или устаревшие события.
- При работе с датами явно учитывай часовой пояс и границы периода.
- Изменения схемы оформляй новыми миграциями Flyway. Не переписывай уже применённые миграции. Учитывай существующие данные при добавлении ограничений.
- Не помещай токены и секреты в код, ответы или логи. Не логируй финансовые данные без необходимости.
- Не изменяй посторонний код и не затирай мои незавершённые изменения.

Проверка результата

- При исправлении ошибки по возможности проверяй сценарий, который её воспроизводит.
- Используй Maven Wrapper: в Windows — .\mvnw.cmd test.
- Не подключай тесты к реальному Telegram без явной необходимости.
- Не утверждай, что код работает или тесты проходят, если проверка не выполнялась.
- Если проверке мешает окружение, укажи конкретную причину.
